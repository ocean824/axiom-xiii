# AXIOM NET: Implementation Domain Specification

## 1. Purpose and Doctrine

AXIOM NET is the foundational networking domain for the AXIOM-XIII platform. Its purpose is to provide a flexible, multi-profile networking architecture that supports diverse game genres—ranging from authoritative action games and rollback fighters to lockstep strategy games and large-shard persistent worlds—without forcing a single networking model onto all projects [1]. The networking stack is designed to be highly modular, allowing developers to select the exact profile that matches their gameplay requirements while leveraging a shared, secure, and robust underlying transport layer. This flexibility is essential for a platform that aims to host everything from fast-paced competitive shooters to massive, persistent virtual economies.

The non-negotiable doctrine governing AXIOM NET is that it must sit above a transport abstraction layer supporting both reliable streams and unreliable datagrams, with built-in congestion control and encryption [1]. Furthermore, per the Owner Directive, all capabilities—including those labeled as "Architected," "Preview," or "future" in the master specification, such as large-shard architectures and persistent event logs—are mandatory V1 implementation scope [2]. They must be fully coded, integrated, and tested, even if their activation is restricted by policy gates [2]. This ensures that the platform is fundamentally capable of supporting its most ambitious networking goals from day one, avoiding the need for costly architectural rewrites in subsequent versions. The system must also strictly adhere to the principle of domain isolation, exposing explicit APIs and never accessing another domain's internal storage directly [1].

## 2. Personas and Actors

The AXIOM NET domain serves a variety of personas and system actors, each interacting with the network stack in distinct ways:

- **Game Developer/Creator**: The primary consumer of the AXIOM NET APIs. They configure the network profile for their project (e.g., rollback, authoritative, async) and define replication policies for game entities. They utilize debugging and bandwidth visualization tools to optimize network performance and ensure a smooth player experience across diverse network conditions.
- **Player/Participant**: The end-user connecting to the network. They send inputs and receive state updates or authoritative corrections. Their experience is directly impacted by the latency, jitter, and packet loss mitigation strategies implemented within the network profiles. The system must provide them with a seamless, responsive experience regardless of their geographical location or connection quality.
- **Dedicated Server/Host**: Acts as the authoritative source of truth for authoritative action profiles and large-shard cells. It is responsible for validating inputs, simulating the authoritative state, broadcasting state updates to connected clients, and enforcing anti-cheat measures.
- **Spectator**: An observer who receives delayed or filtered state updates to watch matches without participating. The system must ensure that spectators cannot gain or share competitive advantages, necessitating strict separation of live competitive information from delayed public views [1]. This role is crucial for esports broadcasting and community engagement.
- **Arena Adjudicator/Policy Engine**: An automated or human-assisted system that consumes tamper-evident match records and deterministic evidence generated by AXIOM NET to resolve disputes, verify match outcomes, and enforce sanctions in competitive environments [1]. This actor relies heavily on the cryptographic integrity and completeness of the data provided by AXIOM NET.

## 3. Domain Boundaries and Interfaces

AXIOM NET interfaces strictly with other AXIOM-XIII domains via explicit APIs, ensuring no direct access to internal storage across boundaries [1]. This strict separation of concerns is critical for maintaining system stability, security, and modularity.

- **AXIOM Engine**: The engine provides the simulation core, ECS (Entity Component System) state, and input history. AXIOM NET is responsible for replicating this state across the network or rolling it back in the event of mispredictions. The engine must expose deterministic simulation capabilities for profiles like rollback and lockstep, allowing AXIOM NET to accurately recreate game states based on historical inputs.
- **AXIOM Protocol**: Defines the stable semantic objects (e.g., `Match`, `Tournament`, `ProvenanceRecord`) that AXIOM NET transports and synchronizes [1]. AXIOM NET relies on these protocol definitions to ensure that data transmitted across the network is universally understood by all AXIOM domains, facilitating seamless interoperability.
- **AXIOM Arena**: Consumes replays and tamper-evident match records generated by AXIOM NET for competitive adjudication [1]. AXIOM NET must guarantee the integrity and provenance of these records to support the Arena's mission of fair competition, accurate ranking, and secure prize pool distribution.
- **AXIOM Services**: Interacts with AXIOM NET for matchmaking handoff, session/lobby management, presence, and cloud saves [1]. When a match is found, AXIOM Services orchestrates the allocation of a dedicated server and hands the connection details over to AXIOM NET, ensuring a smooth transition from matchmaking to active gameplay.
- **AXIOM Chain**: Receives verified match results and state transitions for escrow settlement and digital object updates. AXIOM NET must provide the cryptographic proofs and state attestations required by the Chain to execute these transactions securely, bridging the gap between gameplay outcomes and the platform's economic layer.

## 4. Named Components and Modules

The AXIOM NET architecture is composed of several key modules, each responsible for a specific aspect of the networking stack:

### 4.1 Transport Abstraction Layer
This layer provides the unified interface over reliable streams, unreliable datagrams, congestion control, and encryption. It abstracts underlying protocols (e.g., UDP, WebRTC, future PYRAMID optimized transport) behind AXIOM Secure Transport APIs [1]. It must support connection migration where available, peer-to-peer and relay paths, dedicated servers, and local network connections [1]. This abstraction allows the platform to upgrade its underlying transport mechanisms without requiring changes to game logic or higher-level networking code.

### 4.2 Replication Engine
The core module responsible for synchronizing game state across the network. It must provide:
- State snapshots and delta compression to minimize bandwidth usage.
- Event and RPC (Remote Procedure Call) equivalents for discrete actions.
- Relevance and interest management to ensure clients only receive data for entities they need to know about, reducing both bandwidth and client-side processing load.
- Priority and bandwidth budgets to manage network congestion and ensure critical data is delivered first.
- Prediction, reconciliation, interpolation, and extrapolation to smooth out network latency and provide a responsive feel.
- Dormancy for entities that are not currently active or changing, further optimizing bandwidth.
- Streamed entity handoff for seamless transitions between server nodes in large-shard environments.
- Entity schema versioning to support backward compatibility and seamless updates.
- Server migration architecture to handle host disconnections gracefully.

### 4.3 Profile Implementations
AXIOM NET provides specialized cores for different game genres, acknowledging that a "one size fits all" approach is insufficient for modern game development:
- **Authoritative Core**: Designed for open-world action, shooters, co-op, and RPGs. The server holds the authoritative state, and clients send inputs and receive state corrections. This profile prioritizes security and consistency over absolute client responsiveness.
- **Rollback Core**: Designed for frame-sensitive 2D/3D fighters. It requires a deterministic simulation core, input history, save/restore snapshots, prediction, rollback/resimulation, frame delay configuration, desync detection, and spectator/replay synchronization [1]. This profile prioritizes immediate local responsiveness, resolving conflicts retroactively.
- **Lockstep Core**: Designed for deterministic or semi-deterministic RTS/tactics games. It utilizes lockstep commands, deterministic state, authoritative correction, turn/phase validation, command replay, and large unit aggregation [1]. This profile ensures all clients simulate the exact same state based on synchronized commands.
- **Large-Shard Core**: Designed for persistent worlds with spatial partitioning. It manages spatial cells, distributed authority, interest management, cell handoff, global services separated from cell simulation, entity routing, cross-cell messaging, and a persistent event log [1]. This profile is engineered to support massive concurrency and continuous persistence.
- **Async Core**: Designed for card games, turn-based games, correspondence, and creator workflows. It handles state synchronization over extended periods, often relying heavily on persistent cloud storage and notifications.
- **Local/Offline Core**: Ensures that games can function without network dependency, simulating the network layer locally to maintain code consistency between online and offline modes.

### 4.4 Multiplayer Services Hub
This module handles the orchestration of multiplayer sessions. It provides APIs for sessions/lobbies, party integration, presence, NAT traversal/relay, dedicated server allocation, region selection, cross-play identity, voice/text integration, matchmaking handoff, replays, spectators, server browsers (where permitted), cloud saves, sanctions/ban enforcement, and incident controls [1]. It acts as the bridge between the core gameplay networking and the broader platform services.

### 4.5 Replay and Evidence Generator
Responsible for producing various types of replays and evidence records. It supports input/deterministic replay, authoritative state replay, event replay, video capture, and hybrid replay with game-aware camera and metadata [1]. For competitive games, it must produce tamper-evident match records containing build identity, ruleset, players/teams, inputs or authoritative events, server identity, timing and network conditions, anti-cheat signals, results, signatures/attestations, dispute evidence pointers, and retention policies [1]. This module is critical for supporting the platform's competitive and economic features.

## 5. Canonical Entities and Stable IDs

All network entities and sessions must use AXIOM's stable identifier system to ensure consistency across the platform [1]. Identifiers must remain stable across file moves and renames, providing a reliable foundation for telemetry, tracking, and cross-domain references.

- `NetSessionID`: Uniquely identifies a multiplayer lobby or match. This ID is used to correlate telemetry, replays, and match records across the platform.
- `NetEntityID`: Uniquely identifies a replicated game object across the network. It must be consistent between the server and all connected clients, allowing for accurate state synchronization and RPC routing.
- `MatchRecordID`: Identifies a tamper-evident competitive evidence package. This ID is critical for Arena adjudication, dispute resolution, and historical tracking of competitive outcomes.
- `ShardCellID`: Identifies a specific spatial partition within a large-shard environment. It is used for routing entities, managing cross-cell messaging, and coordinating handoffs between distributed authority nodes.

## 6. State Machines and Transitions

### 6.1 Connection State Machine
The lifecycle of a network connection is managed by a strict state machine to ensure reliable and secure communication, handling edge cases and transient failures gracefully:
- `DISCONNECTED` $\rightarrow$ `CONNECTING`: Initiated when a client attempts to connect to a server. Involves transport handshake and encryption setup.
- `CONNECTING` $\rightarrow$ `AUTHENTICATING`: Transport layer is established; the system now verifies the identity of the connecting client using platform authentication services.
- `AUTHENTICATING` $\rightarrow$ `CONNECTED`: Identity is verified; the client joins the session, and replication begins.
- `CONNECTED` $\rightarrow$ `RECONNECTING`: Triggered by transient packet loss, connection migration, or host migration. The system attempts to restore the connection without dropping the user from the game.
- `RECONNECTING` $\rightarrow$ `CONNECTED`: The connection is successfully re-established or migrated, and normal gameplay resumes.
- `RECONNECTING` $\rightarrow$ `DISCONNECTED`: The reconnection attempt times out, and the client is formally dropped from the session.

### 6.2 Rollback State Machine
For games utilizing the Rollback Core, the simulation state is managed dynamically to hide latency and provide a responsive feel, even in the face of network delays:
- `SYNCED` $\rightarrow$ `PREDICTING`: The local client applies inputs ahead of receiving confirmation from the remote peer or server, assuming no deviation from expected behavior.
- `PREDICTING` $\rightarrow$ `ROLLBACK_TRIGGERED`: Remote inputs arrive and diverge from the local prediction, indicating a desync that must be corrected.
- `ROLLBACK_TRIGGERED` $\rightarrow$ `RESIMULATING`: The system restores the last known good snapshot and reapplies all inputs up to the current frame, recalculating the correct state.
- `RESIMULATING` $\rightarrow$ `SYNCED`: The local state is reconciled with the authoritative state, and normal prediction resumes.

## 7. Data Ownership and Storage

AXIOM NET operates primarily in the **game runtime data plane** [1]. It does not persistently store game state; it routes, replicates, and synchronizes it in real-time. Persistent data, such as cloud saves, account profiles, and persistent event logs for large shards, are handed off to AXIOM Services (object storage) and AXIOM Protocol (ledgers) [1]. AXIOM NET must ensure that any data it temporarily buffers or caches is securely wiped when no longer needed, adhering to the platform's privacy and security guidelines. The network layer must never become a bottleneck for data persistence, relying instead on specialized storage domains.

## 8. Failure and Degraded Modes

The network architecture must be resilient to various failure conditions and network anomalies, providing a graceful degradation of service rather than catastrophic failure:
- **High Latency/Jitter**: The replication engine must dynamically increase interpolation buffers to smooth out movement. The rollback core must adjust frame delay configurations to minimize the frequency and severity of rollbacks, balancing responsiveness with visual stability [1].
- **Host/Server Crash**: The connection state machine must transition to `RECONNECTING`. The multiplayer services hub must attempt host migration (in peer-to-peer setups) or request dedicated server reallocation (in client-server setups) without dropping the session entirely, aiming for seamless recovery [1].
- **Cross-Cell Handoff Failure**: In large-shard profiles, if an entity fails to hand off to an adjacent cell, it must route to a fallback global service or gracefully degrade to a dormant state until the target cell recovers, preventing data loss or duplication and maintaining world integrity [1].
- **Bandwidth Saturation**: The replication engine must strictly enforce priority and bandwidth budgets, dropping low-priority updates (e.g., distant cosmetic entities) to ensure critical gameplay data (e.g., player movement, combat events) is transmitted reliably [1].

## 9. Security, Privacy, and Provenance

Security is a foundational requirement for AXIOM NET, particularly given its integration with real-value competition and digital objects. The network layer must act as the first line of defense against malicious actors:
- **Anti-Cheat and Integrity**: Every networked state must declare a cheat sensitivity policy. Arena-approved games must generate tamper-evident match records containing anti-cheat signals, inputs, and cryptographic signatures to support post-match adjudication and automated sanctioning [1].
- **Spectator Isolation**: Spectator mode must strictly separate live competitive information from delayed/public views. This is critical to prevent coaching, stream sniping, or information leaks that could compromise the integrity of a match, especially in high-stakes tournaments [1].
- **Encryption**: All transport must be encrypted by default, utilizing established cryptographic primitives. No unreviewed cryptography may be used, ensuring that all data in transit is protected against eavesdropping and tampering [1].
- **Privacy**: AXIOM NET must adhere to the platform's privacy and telemetry defaults, ensuring that sensitive user data is not inadvertently exposed or logged without consent, complying with global privacy regulations [1].

## 10. Observability and Telemetry

AXIOM NET must integrate deeply with the platform's telemetry plane to provide comprehensive observability for both developers and platform operators, enabling rapid diagnosis of network issues:
- **Metrics**: Must collect and report metrics for baseline latency, high latency, jitter, packet loss, reorder, duplication, bandwidth consumption, desync events, and rollback frames [1]. These metrics must be aggregated and visualized in real-time dashboards.
- **Developer Tools**: Must provide debugging and bandwidth visualization tools to help creators optimize their replication policies, identify network bottlenecks, and tune their games for diverse network conditions [1].
- **Correlation**: All network events and logs must be tagged with the appropriate `NetSessionID` and `NetEntityID` to allow for cross-domain correlation and incident investigation, ensuring that network issues can be traced back to specific game events or user actions [1].

## 11. Performance and Resource Budgets

- **Bandwidth**: The replication system must enforce strict priority and bandwidth budgets per entity and per connection to ensure fair and efficient use of network resources, preventing single entities or players from degrading the experience for others [1].
- **Concurrency**: The large-shard architecture must be designed to support 10,000-plus logical participants within a logical shard. However, a production V1 concurrency number must only be published after measured tests on defined hardware and game workloads, ensuring that performance claims are grounded in empirical evidence [1].

## 12. Test Pyramid and Acceptance Tests

Robust testing is mandatory for all networked projects. The AXIOM NET domain must provide the infrastructure to support these tests, ensuring that games are resilient to real-world network conditions:
- **Network Conditions**: Tests for baseline latency, high latency, jitter, packet loss, reorder, duplication, and bandwidth caps must be automated and run continuously [1].
- **Resiliency**: Tests for disconnect/reconnect flows, host/server crashes, and host migration must verify that the system can recover gracefully from unexpected failures [1].
- **Security and Integrity**: Tests for version mismatches, malicious packets, clock skew, and cross-region behavior must ensure that the network layer cannot be exploited by bad actors [1].
- **Scale**: Load testing with synthetic clients for large-shard cells to validate distributed authority, cell handoff mechanisms, and overall system scalability under extreme load [1].

## 13. V1 Definition of Done

Per the Owner Directive and the master specification, AXIOM NET is considered "Done" for V1 when the following criteria are met, ensuring a complete and robust implementation:
1. All network profiles (Authoritative, Rollback, Lockstep, Async, Large-Shard, Local) are fully coded, integrated, and tested [2]. No profile may be left as a documentation-only placeholder.
2. The transport abstraction layer supports both reliable streams and unreliable datagrams with encryption, congestion control, and connection migration [1].
3. Replays, spectating, and deterministic evidence generation are fully operational and integrated with AXIOM Arena, supporting the platform's competitive ecosystem [1].
4. The large-shard architecture, including spatial cells, distributed authority, and cross-cell messaging, is implemented and tested with synthetic clients [1].
5. The system is executable, integrated into the CI pipeline, and all mandatory ADRs (e.g., networking transport and dedicated server orchestration) are resolved [1].
6. The implementation provides the necessary APIs and schema contracts for CodeSpring and human engineers to build upon without guessing, facilitating parallel development [2].

## 14. Work Packages in Dependency Order

The implementation of AXIOM NET must proceed in the following dependency order to ensure a stable foundation and minimize integration risks:
1. **Transport Abstraction**: Implement AXIOM Secure Transport APIs over reliable/unreliable protocols, including encryption and congestion control. This forms the bedrock of all subsequent networking features.
2. **Replication Core**: Build state snapshots, deltas, interest management, priority budgeting, and entity schema versioning. This layer handles the mechanics of data synchronization.
3. **Profile Implementations**: Develop Authoritative, Rollback, and Lockstep cores, ensuring deterministic simulation capabilities where required. These profiles define how game logic interacts with the network.
4. **Multiplayer Services**: Integrate sessions, matchmaking handoff, dedicated server allocation, and NAT traversal. This module connects the core networking to the platform's social and matchmaking systems.
5. **Large-Shard Architecture**: Implement spatial cells, distributed authority, cross-cell messaging, and persistent event logs. This represents the most complex networking challenge and relies on the stability of the lower layers.
6. **Evidence & Replays**: Build tamper-evident match records, spectator isolation, and integration with AXIOM Arena. This package secures the competitive integrity of the platform.
7. **Testing & Telemetry**: Implement the network test profiles, synthetic client load testing, and bandwidth visualization tools. This final package ensures the system is observable, tunable, and robust.

## 15. Open ADRs

The following Architectural Decision Records (ADRs) must be resolved to finalize the AXIOM NET implementation and guide future development:
- **ADR-010**: Networking transport and dedicated server orchestration [1]. This ADR must define the specific underlying protocols (e.g., WebRTC, custom UDP) and the orchestration strategy for spinning up and managing dedicated server instances across multiple cloud providers. It must address how AXIOM NET will scale globally while maintaining low latency and high reliability.
